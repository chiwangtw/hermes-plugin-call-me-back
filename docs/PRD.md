# PRD — call-me-back

**Status**：v0.1：以 Hermes 為調度者、Orca 為終端管理器，支援 Claude Code／Codex／pi；參考部署為 Windows 上的 Hermes × macOS 上的 Orca，三種執行者都經實測
決策與機制見 `ADR.md`；名詞以 `../CONTEXT.md` 為準。

## 1. 問題
調度者 agent 把工作派給 CLI coding agent 之後，看不到、碰不到那些 Session；Session 停下時也沒人知道。人只能「等一下再去看」，調度者也無法自己接手。每換一種 CLI agent，這件事就要重接一次。

## 2. 角色
- **人**：這些 Session 的擁有者
- **調度者**：派工的 agent。只服務 Hermes agent 的使用者
- **執行者**：CLI coding agent。必須支援 Claude Code、Codex、pi
- **終端管理器**：Session 所在的終端管理工具，例如 Orca、tmux

## 3. 範圍：只提供可達性
本專案只定義「做得到什麼」。**怎麼用**（何時派工、怎麼驗收、回報寫什麼、佇列與排程）不在範圍內，交給任務管理類 skill、範例（recipe）或調度者當下判斷。

## 4. 使用情境
- **S1 同機**：調度者與執行者在同一台機器
- **S2 雙機**：調度者在常開的機器，執行者在另一台（筆電、雲端 VM）
- **S3 混用執行者**：同一個調度者同時派給不同種類的 CLI agent（例如同題比稿、寫完換另一種 agent review）
- **S4 遠端駕駛**：人只拿手機，透過調度者看畫面、回話
- **S5 人插手**：人直接進 Session 操作；要讓調度者退出時，由人關閉 Task

## 5. 功能
- **F1** 列出 Session、讀畫面
- **F2** 對 Session 送字、中斷；派工時開 Session，需要時先開一個新的 worktree
- **F3 通知**：追蹤中的 Session 停下時，人在自己選的通訊平台收到訊息
- **F4 叫醒**：追蹤中的 Session 停下時，派工對話開新的一輪接手
- **F5 停下原因**：通知分得出「回合結束」「等批准」「Session 退出」；執行者本身沒有對應訊號的，至少要有「回合結束」
- **F6 關閉 Task**：人或調度者用一個動作結束 Task，這是 Task 結束的唯一方式；在這之前每次停下都通知並叫醒（S5）
- **F7 安裝與自我測試**：照文件安裝後，一個指令確認 F3／F4 整條路通
- **F8 接續**：已退出的 Session 被接回來後，延續原本的 Task，不論是誰接的

## 6. 支援範圍
| 項目 | v0.1 | 之後 |
|---|---|---|
| 執行者 | Claude Code、Codex、pi | Gemini CLI、OpenCode、Cursor CLI 等 |
| 調度者 | Hermes agent | —（不做其他調度者） |
| 終端管理器 | Orca | tmux、zellij 等 |
| 拓樸 | 同機、雙機 | 一個調度者對多台執行機 |
| 作業系統 | 調度機：macOS／Linux／Windows；執行機：macOS／Linux | 執行機在 WSL |
| 通知與叫醒的文字 | 英文（預設）、繁體中文，由使用者設定 | 其他語言 |

新增一種執行者時，應該只要在執行機加一個轉接，不需改動調度者端（v0.1 尚未達成，見第 10 節）。

## 7. 隱私與安全要求
- repo 與 git 歷史不含任何個人識別資料：通訊平台 id、主機名、帳號路徑、內部網路名稱、人名
- 與環境有關的值一律從使用者設定讀取；repo 只附範例設定
- 祕密不落明碼、不進 repo
- 執行者的輸出送進調度者對話時一律標示為資料，不當指令
- 調度者送往執行機的文字（要打進 Session 的字、標題、路徑）只會被原樣傳遞，不會在執行機被當成指令執行
- 通知與 log 不含派工對話的識別資訊（例如聊天平台的 chat id）

## 8. 驗收
- F1／F2：Claude Code、Codex、pi 各開一個 Session，在每個支援的終端管理器上都能列出、讀畫面、送一句話並被 agent 收到
- F2：含引號、中文、shell 特殊字元的文字原樣送達 Session，而且不在執行機上被執行
- F2：派工到終端管理器還不認得的目錄，也能開出 Session
- F2：派出去的 Session 卡在啟動提問（例如資料夾信任）時，調度者在派工結果裡就得知，不必等叫醒
- F3：三種執行者的追蹤中 Session 停下 → 人收到通知，通知標明執行者種類與 task
- F4：三種執行者的追蹤中 Session 停下 → 派工對話不需人發訊息就自動接手
- F4：Task 關閉前，同一個 Session 第二次、第三次停下仍會叫醒
- F4：同一串同時等多個 task，每個停下都各自叫醒，不混淆
- F4：調度機的 gateway 重啟後，未關閉的 Task 再停下仍會叫醒原本的派工對話
- F5：Claude Code、Codex 卡在批准時，人收到「等批准」而非「回合結束」
- F5：Session 退出（正常或當掉）時，人收到通知、派工對話被叫醒，停下原因標為「Session 退出」
- F6：Task 關閉後，該 Session 和它的接續再停下，不再通知、不再叫醒
- F6：人在追蹤中的 Session 打字後，它停下仍會叫醒派工對話（人插手不會自動關閉 Task）
- F7：在乾淨機器照文件安裝，10 分鐘內通過自我測試
- F8：Session 退出、隔一段時間後被人或調度者接回來，再停下時仍通知並叫醒原本的派工對話
- 人自己開的 Session 不觸發 F3／F4，就算和追蹤中的 Session 在同一個工作目錄也一樣
- 派出去的 Session 裡再啟動的其他種類 agent，不會替這個 Task 產生停下事件
- 兩種拓樸下，連線中斷或調度機的 gateway 停機時事件不遺失、恢復後補到，且不重複推
- S1 同機拓樸不需任何網路或金鑰設定
- 發佈前掃描 repo 與 git 歷史，無第 7 節所列個人識別資料

## 9. 非目標
- 派工策略、驗收標準、回報格式、佇列與排程
- 代替人回答批准
- UI／儀表板
- 取代 Orca、tmux 等終端管理器
- 支援 Hermes 以外的調度者；沒有 Hermes、只要通知的使用者

## 10. 待辦
- 終端管理器只做了 Orca；tmux 之後再做
- F2：還不能關 Session、關 worktree
- F7：還沒有一個指令走完 F3／F4 整條路的自我測試；目前靠單元測試與手動驗收
- 新增執行者仍要改調度者端的執行者清單（第 6 節）
- 一個調度者對多台執行機
- 調度機 gateway 停機期間的補處理：設計上事件會留在 inbox，尚未實測
- Hermes 每次升級都要回歸測試叫醒（依賴非公開 API，見 ADR 0003）
- 已知缺口：沒經過派工 wrapper 的接續，在 `/clear`／`/new` 之後就不再追蹤；同種執行者以子行程啟動時，會被當成派出去的那個 Session（見 ADR 0005）
