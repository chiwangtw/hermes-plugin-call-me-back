# 0001 分成兩種推送：通知與叫醒

**Status**：accepted（2026-09-25）

追蹤中的 Session 停下時，有兩個對象要知道：人（可能不在電腦前），以及要接手的派工對話。兩者要的東西不同：人要的是「它停了、停在哪」，派工對話要的是一個新的回合，讓調度者自己接下去。

做法：

- **通知**：推一則訊息給人。走 Hermes 的 `deliver_only` webhook route，直接送到人選的聊天位置（例如一個 Telegram topic），不經過調度者，零 token。
- **叫醒**：讓派工對話開新的一輪接手，做法見 0003。
- 兩者互相獨立。只要 Task 還沒關閉，每次停下都各自觸發，不是只有做完才觸發。
- 通知可以關掉（不設通知的 route），只留叫醒。

為什麼：

- 通知不依賴調度者。調度者出錯、被叫醒卻沒回、或叫醒送不進去時，人仍然知道 Session 停了，通知就是備援。
- 通知不花 token，每次停下都送也沒有成本。

考慮過但沒採用：

- 由 webhook 另起一個 agent run 做驗收，再把結果推給人：那個 run 是獨立的 session，派工對話看不到它說了什麼，也接不下去。
- 只叫醒、由調度者轉告人：調度者一出問題，人就什麼都收不到；而且每次轉告都花 token。

代價：

- 叫醒生效時，人每次會收到兩則：一則通知，一則調度者被叫醒後的回覆。
- Hermes 沒有讓 plugin 直接發訊息給人的 API，所以通知要經過一條 webhook route，gateway 環境裡也要有 webhook 的簽章密鑰。
